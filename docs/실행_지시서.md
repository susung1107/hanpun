# 한푼 프론트엔드 — 로컬 실행 지시서

작성일 2026-07-28 · 대상: 수성의 Mac · 프론트엔드 v1.0 (M2~M5 UI 완료분)

---

## 0. 이 문서가 하는 일

Claude 가 클라우드에서 완성한 한푼 React Native 프론트엔드를 **당신 Mac 에서 실제로 띄우는 것**까지 안내한다. 서버는 아직 필요 없다. `USE_MOCK_API = true` 상태라 앱 혼자 목 데이터로 완전히 동작한다.

소요 시간은 처음 한 번이 15~25분 정도(대부분 `pod install` 대기), 그다음부터는 30초다.

## 1. 사전 준비 확인

터미널에서 아래를 실행해 전부 값이 나오는지 본다.

```bash
node -v          # v20 이상 (권장 v22)
pnpm -v          # 10 이상 — 없으면: npm i -g pnpm
ruby -v          # 3.x
bundler -v       # 없으면: gem install bundler
xcodebuild -version
```

CocoaPods 를 `brew` 로 따로 깔 필요는 없다. `apps/mobile/Gemfile` 이 검증된 CocoaPods 버전을 고정해 두었고(빌드를 깨뜨리는 버전들이 실제로 있다) Bundler 가 그 버전을 설치한다. 이게 React Native 공식 템플릿 방식이다.

Xcode 는 App Store 버전으로 설치되어 있고, **한 번 실행해서 라이선스 동의 + iOS 시뮬레이터 다운로드**까지 끝난 상태여야 한다. Xcode → Settings → Platforms 에서 iOS 시뮬레이터가 있는지 확인한다.

Watchman 이 있으면 Metro 가 빨라진다(선택): `brew install watchman`

## 2. 압축 풀기

전달받은 `hanpun-frontend.zip` 을 원하는 개발 폴더에 푼다. 권장 위치는 `~/dev/hanpun` 이다(백엔드 코칭 문서와 경로가 일치한다).

```bash
mkdir -p ~/dev
cd ~/dev
unzip ~/Downloads/hanpun-frontend.zip -d hanpun
cd hanpun
ls        # apps  packages  CLAUDE.md  docker-compose.yml  package.json ...
```

`ls` 결과에 `apps` 와 `packages` 가 보이면 정상이다. 만약 `hanpun/hanpun/apps` 처럼 한 겹 더 들어가 있으면 안쪽 폴더 내용을 밖으로 꺼낸다.

> zip 에는 `node_modules` 와 `ios/Pods` 가 들어 있지 않다. 다음 단계에서 직접 설치한다. 이게 정상이고 올바른 방식이다.

## 2-1. 폴더가 왜 이렇게 생겼나 — 그리고 어디서 명령을 치는가

`apps/mobile` 이 따로 있는 게 맞다. 한푼은 **pnpm 모노레포**다. 앱과 서버가 타입·포맷·카테고리 정의를 공유해야 하기 때문에(같은 `Transaction` 타입을 양쪽이 두 번 적으면 반드시 어긋난다) 한 저장소에 넣고 공용 코드를 `packages/shared` 로 뺐다.

```
~/dev/hanpun/            ← 저장소 최상위. 명령은 여기서 친다
├── package.json         전체 스크립트 (ios, android, typecheck, lint, db:up ...)
├── pnpm-workspace.yaml  어떤 폴더가 워크스페이스인지 선언
├── apps/
│   ├── mobile/          React Native 앱 = @hanpun/mobile  ← 화면 코드는 여기 src/
│   └── server/          NestJS 서버 = @hanpun/server (B1 에서 당신이 만든다. 아직 없음)
├── packages/
│   └── shared/          앱·서버 공용 타입·유틸 = @hanpun/shared
└── docs/                이 문서 등
```

**규칙 하나만 기억하면 된다: 명령은 항상 `~/dev/hanpun` 에서 친다.** `apps/mobile` 로 들어가서 `pnpm install` 을 하면 워크스페이스 링크가 안 걸려서 Metro 가 `@hanpun/shared` 를 못 찾는다. 최상위 `package.json` 에 짧은 별칭 스크립트를 만들어 둔 이유가 이것이다.

| 최상위에서 치는 명령 | 실제로 하는 일 |
| --- | --- |
| `pnpm install` | 워크스페이스 전체 설치 + `@hanpun/shared` 링크 |
| `pnpm ios` / `pnpm android` | `apps/mobile` 의 앱 실행 |
| `pnpm start` | Metro 번들러만 따로 실행 |
| `pnpm pods` | iOS 네이티브 의존성 설치 |
| `pnpm typecheck` · `pnpm lint` · `pnpm test` | 검증 3종 (모든 워크스페이스) |
| `pnpm --filter @hanpun/mobile <스크립트>` | 특정 워크스페이스의 스크립트 직접 실행 |
| `pnpm db:up` / `pnpm db:down` | MySQL 8 컨테이너 (서버 작업 때) |

예외는 딱 하나, 다음 단계의 `bundle install` 이다. 이건 Ruby 젬이라 `apps/mobile` 안에서 실행한다.

## 3. 의존성 설치

```bash
cd ~/dev/hanpun
pnpm install
```

`lucide-react-native` 의 `unmet peer react@^18` 경고가 뜨는데 **무시해도 된다**. 아이콘 컴포넌트가 React 19 에서 정상 동작하는 것을 확인했다.

`Tarball download average speed ...` 같은 WARN 도 무시해도 된다. npm 레지스트리에서 특정 파일(`prettier` 등)이 느리게 내려왔다는 알림일 뿐, 설치 결과와는 무관하다.

`pnpm-workspace.yaml` 에 `onlyBuiltDependencies: [sharp]` 가 들어 있다. pnpm 10 은 의존성의 postinstall 스크립트를 기본으로 차단하는데(공급망 공격 방어), `sharp` 는 스플래시 에셋 생성 CLI 가 실제로 필요한 네이티브 바이너리를 이때 받는다. 이 줄이 없으면 `Ignored build scripts: sharp@0.32.6` 경고가 뜨고 6-1 단계에서 실패한다. 이미 그 경고를 본 상태라면 `pnpm install` 을 한 번 더 돌리면 된다.

이어서 iOS 네이티브 의존성. **먼저 Ruby 젬(CocoaPods)을 깔고**, 그다음 Pod 을 설치한다. 순서가 중요하다 — `pods` 스크립트가 `bundle exec pod install` 이라서 젬이 없으면 `Could not find gem` 으로 멈춘다.

```bash
cd ~/dev/hanpun/apps/mobile
bundle install       # 최초 1회 (Gemfile 의 CocoaPods 설치)
cd ~/dev/hanpun
pnpm pods            # 이후로는 이 줄만
```

CocoaPods 가 처음이면 스펙 저장소를 내려받느라 5~15분 걸린다. 커피 한 잔 마실 시간이다. `Pod installation complete!` 가 나오면 끝.

## 4. 실행

```bash
pnpm ios
```

시뮬레이터가 뜨고 Metro 번들러가 별도 창에서 돌아간다. 첫 빌드는 3~8분, 이후는 훨씬 빠르다.

Android 로 보려면 Android Studio 에뮬레이터를 먼저 띄우고:

```bash
pnpm android
```

### 잘 떴다면 보이는 것

온보딩 화면(로고 + "3초면 끝나요") → 시작하기 → 홈. 홈에는 이번 달 지출 요약과 목 거래 몇 건이 들어 있다. 하단 탭 4개(홈 · 캘린더 · 통계 · 설정)가 모두 동작하고, 우하단 + 버튼으로 입력 화면이 열린다. 설정 → 테마에서 다크 모드로 바꿔 보면 전 화면이 함께 전환된다.

## 5. 막혔을 때

**`pod install` 이 실패한다**

```bash
cd ~/dev/hanpun/apps/mobile/ios
pod repo update
pod install
```

그래도 안 되면 `rm -rf Pods Podfile.lock` 후 다시 `pod install`.

**빌드가 캐시 때문에 깨진 것 같다**

```bash
cd ~/dev/hanpun/apps/mobile
rm -rf ios/build
watchman watch-del-all 2>/dev/null
npx react-native start --reset-cache
# 다른 터미널에서
pnpm ios
```

**Metro 가 `@hanpun/shared` 를 못 찾는다**

`pnpm install` 을 **저장소 최상위**(`~/dev/hanpun`)에서 실행했는지 확인한다. `apps/mobile` 안에서 실행하면 워크스페이스 링크가 안 걸린다. 이미 그랬다면 `apps/mobile/node_modules` 를 지우고 최상위에서 다시 설치한다.

```bash
rm -rf ~/dev/hanpun/apps/mobile/node_modules
cd ~/dev/hanpun && pnpm install
```

**`pod install` 이 `Invalid Podfile file` + `[Codegen] Error: ... must be of type React.ElementRef<>` 로 멈춘다**

`react-native-screens` 버전 문제다. 4.26.0 이 추가한 안드로이드 툴바 커맨드가 RN 0.82 의 코드젠 문법을 쓰는데 이 프로젝트는 RN 0.81 이라 파서가 거부한다. `apps/mobile/package.json` 의 값이 `4.25.2` 정확 고정인지 확인한다. `^4.10.0` 처럼 캐럿이 붙어 있으면 v1.4 이전 zip 이므로 그 줄을 아래처럼 고치고 다시 설치한다.

```json
"react-native-screens": "4.25.2",
```

```bash
cd ~/dev/hanpun && pnpm install && pnpm pods
```

**`bundle exec pod install` 이 `Could not find gem` 으로 멈춘다**

`apps/mobile` 안에서 `bundle install` 을 먼저 실행한다 (3 단계). Bundler 자체가 없으면 `gem install bundler`.

**시뮬레이터에 앱이 흰 화면으로만 뜬다**

Metro 창의 에러를 먼저 본다. `Unable to resolve module` 계열이면 위의 캐시 초기화, 빨간 화면이면 그 메시지를 그대로 Claude 에게 보내면 된다.

**`nativewind` 나 `react-native-screens` 를 업데이트하고 싶어진다**

하지 말자. 둘 다 캐럿 없는 정확 고정(`4.1.23` · `4.25.2`)이 의도된 것이다. nativewind 4.2 이상은 Reanimated 4 의 `react-native-worklets/plugin` 을 요구해 번들이 아예 안 만들어지고, screens 4.26 이상은 위의 코드젠 오류를 낸다. 각각 Reanimated 4 · RN 0.82 로 올릴 때 함께 푼다. 자세한 배경은 `CLAUDE.md` 3-2 에 있다.

## 6-1. 당신 Mac 에서 한 번 해야 하는 것 — 스플래시 네이티브 연결

`react-native-bootsplash` 는 설치되어 있고 JS 쪽(`BootSplash.hide()`)도 이미 붙어 있지만, **네이티브 스플래시 화면 자체는 아직 RN 기본값이다.** 이 파일들은 손으로 고치면 안 되는 자리라서(존재하지 않는 스타일을 참조하게 되면 안드로이드 빌드가 깨진다) 에셋 생성 명령으로 만들어야 한다. Mac 에서 딱 한 번 실행하면 된다.

```bash
cd ~/dev/hanpun/apps/mobile
npx react-native-bootsplash generate <로고파일>.png \
  --platforms android,ios --background '#EB6834' --logo-width 120
cd ios && pod install && cd ..
```

이 명령은 내부적으로 `sharp` 로 이미지를 여러 해상도로 굽는다. 3 단계의 `onlyBuiltDependencies` 설명대로 승인이 되어 있어야 동작한다. `Something went wrong installing the "sharp" module` 이 뜨면 저장소 최상위에서 `pnpm install` 을 한 번 다시 돌린다.

로고 PNG(투명 배경, 최소 1024×1024)가 아직 없으면 이 단계는 출시 준비 때로 미뤄도 된다. 지금은 흰 스플래시가 잠깐 스쳐 보일 뿐 동작에는 영향이 없다. 로고 파일이 준비되면 알려주면 필요한 옵션을 같이 맞춰 준다.

## 7. 서버로 갈아타는 법 (M1 이후)

1. `apps/mobile/src/config.ts` 의 `USE_MOCK_API` 를 `false` 로 바꾼다.
2. 서버를 `localhost:3000` 에 띄운다 (`API_BASE_URL` 이 개발 모드에서 자동으로 여기를 본다. Android 에뮬레이터는 `10.0.2.2` 로 자동 분기).
3. `pnpm ios` 재실행.

목 API 는 삭제하지 않는다. 서버가 죽었을 때 UI 작업을 계속하려면 다시 `true` 로 돌리면 된다.

`src/mocks/api.ts` 의 함수 시그니처가 곧 API 계약서의 응답 형태다. 서버를 여기에 맞추면 프론트는 손댈 게 없다.

## 8. Claude Code 연동

### 8-1. 왜 Claude Code 가 필요한가

지금 이 대화(클라우드 세션)는 당신 Mac 의 파일에 직접 접근할 수 없다. 그래서 코드는 클라우드에서 쓰고 검증해서 zip 으로 넘기는 방식이었다. 이 방식의 한계는 **시뮬레이터를 띄워 볼 수 없다는 것** — 렌더링이 어긋나거나 Xcode 빌드가 깨지면 클라우드에서는 재현조차 못 한다.

Claude Code 는 당신 Mac 의 터미널에서 돌기 때문에 그 자리를 메운다. `pnpm ios` 를 직접 돌리고, Metro 의 빨간 화면을 직접 읽고, 고치고, 다시 빌드한다. 앞으로 역할은 이렇게 갈린다.

| | 이 대화 (클라우드) | Claude Code (당신 Mac) |
| --- | --- | --- |
| 기획 · 설계 · 문서 · API 계약서 | 담당 | — |
| 프로젝트 문서 · Google Drive 발급 | 담당 | — |
| 새 화면 · 새 기능 코드 작성 | 담당 | 가능 |
| 빌드 · 시뮬레이터 실행 · 런타임 오류 수정 | 불가 | **담당** |
| 백엔드 실습 코칭 | 설명 · 코드 리뷰 | 옆에서 함께 작성 |

### 8-2. 설치

먼저 이미 깔려 있는지 본다.

```bash
claude --version     # 버전이 나오면 설치 완료
```

`command not found` 면 공식 네이티브 설치 스크립트를 쓴다(권장 방식이고 자동 업데이트된다).

```bash
curl -fsSL https://claude.ai/install.sh | bash
```

Homebrew 를 쓰고 싶으면 `brew install --cask claude-code` 도 된다(대신 자동 업데이트는 안 된다). 설치가 끝나면 진단을 한 번 돌려 본다.

```bash
claude doctor
```

```bash
claude
```

첫 실행에서 브라우저가 열리고 로그인하면 된다. **반드시 `~/dev/hanpun` 안에서 실행한다** — 저장소 최상위의 `CLAUDE.md` 를 자동으로 읽어 프로젝트 규칙(NativeWind 우선, FlatList 전용, `nativewind` 4.1.23 고정, 컴포넌트 `index.ts` 진입점, 금액 포맷터 위치, 에러 처리 규칙, 커밋 전 검증 3종)을 그대로 따르기 때문이다. 상위 폴더에서 실행하면 이 규칙이 적용되지 않는다.

첫 커밋을 아직 안 했다면 먼저 해 둔다. Claude Code 가 무엇을 바꿨는지 `git diff` 로 확인할 수 있어야 되돌리기가 쉽다.

```bash
git init
git add .
git commit -m "한푼 프론트엔드 초기 구현"
```

### 8-4. 첫 지시로 뭘 시킬까

붙였으면 이렇게 시작하는 게 좋다.

```
pnpm install 과 pnpm --filter @hanpun/mobile pods 를 실행하고,
iOS 시뮬레이터로 앱을 띄워서 온보딩 → 홈 → 탭 4개까지 동작하는지 확인해 줘.
빌드나 런타임 오류가 나면 CLAUDE.md 규칙을 지키면서 고치고,
고친 뒤에는 pnpm typecheck · pnpm lint · pnpm --filter @hanpun/mobile test 를 다시 통과시켜 줘.
```

### 8-5. 두 쪽이 어긋나지 않게 하는 규칙

Claude Code 가 로컬 코드를 고치면, **그 순간부터 정본은 당신 Mac 의 저장소다.** 클라우드 사본은 뒤처진다. 그래서:

- Claude Code 가 무엇을 고쳤는지 **커밋 메시지나 `git diff` 를 이 대화에 붙여 준다.** 그러면 클라우드 사본도 맞춰 두고, 이후 문서·설계가 실제 코드와 어긋나지 않는다.
- 더 편한 방법은 GitHub 저장소를 만들어 push 하는 것이다. 그러면 어느 쪽에서 작업하든 한 곳을 본다. 준비되면 저장소 생성부터 같이 하면 된다.
- `CLAUDE.md` 는 두 쪽이 공유하는 유일한 규칙 문서다. 규칙이 바뀌면 이 파일을 먼저 고친다.
